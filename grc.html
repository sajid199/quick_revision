Implementation & Post-Installation Setup

Post-Installation Steps

  1. Check required software components.
    • GRC system: GRCFND_A, GRCPINW
    • Plug-in system: GRCPINW (Non-HR) / GRCPIERP (HR)
  2. Check BC Sets related to *GRAC* and *MSMP* are activated. A BC Set is an SAP-predefined default/standard values container. T-code: SCPR20, Table: SCPRACTST (SCPR*).
    • GRAC*REQUEST* → related to ARM
    • GRAC*ROLE_MGMT* → related to BRM
    • GRAC*RA_RULESET* → related to ARA
    • GRAC*SPM* → related to EAM
    • GRC*MSMP* → related to ARM
  3. Check services related to *GRAC* and *NWBC* are activated — T-code SICF.
  4. SPRO → GRC → General Settings → Activate applications in client — ensure GRC-AC is Active.
  5. SPRO → GRC → General Settings → Workflow → Perform Automatic Workflow Customizing (SWU3) — everything should show green; otherwise escalate to Basis.
  6. SPRO → GRC → General Settings → Workflow → Perform Task-Specific Customizing — every task must be defined as Background or General Task; if left empty, define it as General Task.

Connector Configuration

Prerequisite: an RFC user ID is needed in the plug-in system (S/4HANA/ECC), of type SYSTEM or COMMUNICATION, assigned the necessary RFC authorizations — objects starting with S_RFC* grant RFC-related access.

Path for the first 3 steps: SPRO → GRC → Common Component Settings → Integration Framework

  1. Create Connector (SM59) — sets up RFC between the plug-in and GRC systems.
  2. Maintain Connectors and Connection Types
    • Define Connectors: source connector & logical port should match the target connector.
    • Define Subsequent Connector — only required for JAVA systems, not ABAP; created by the Basis team.
    • Define Connector Groups and create a group, then assign the connector to that group.
  3. Maintain Connection Settings — Access Control integration scenarios: AUTH (BRM, ARA), PROV (ARM), ROLMG (BRM), SUPMG (EAM). Path: SPRO → GRC → Access Control.
  4. Maintain Configuration Settings — SPRO → GRC → AC → Maintain Configuration Settings; adjust parameters that control Access Control functionality per compliance/security policy.
  5. Maintain Connector Settings — SPRO → GRC → AC → Maintain Connector Settings; define Application Type, Environment, and PSS (Password Self Service).
  6. Maintain Mapping for Actions and Connector Groups (same path as step 4)
    • Maintain Connector Group Status — enter the connector group name and activate it.
    • Assign a default connector to the connector group — only one default connector per group per action; all systems in the group should be mapped to all actions.
  7. Maintain Plug-In Settings (plug-in system only) — SPRO → IMG → GRC Plug-In → Maintain Plug-In Configuration Settings.

Synchronization Jobs

Path: SPRO → IMG → GRC → Access Control → Synchronization Jobs

  • Authorization Sync: syncs backend system SU24 data into the GRC system.
  • Repository Object Sync: syncs roles, users & profiles.

MSMP Workflow Overview

User provisioning uses an approval workflow to automate the process. The engine driving it is MSMP — Multi-Stage Multi-Path. The Initiator determines the path a request takes; a single request can split across multiple paths.

Initiator
Decides which path the request will follow.
Rules
Criteria evaluated for path decisions.
Path
A linear group of stages that determine which approvals are required.
Stage
A defined approval action required within a path.
Paths can be split by
  • System: Development vs. Production
  • Role selection: Display vs. Update

Rule Set

Definition: rule sets are collections of rules that identify potential SoD conflicts — each rule defines a combination of actions/transactions that could lead to unauthorized activity or financial misrepresentation if held by a single user.

Purpose: rule sets help maintain internal controls and protect sensitive data, acting as the baseline for risk analysis and remediation.

Rule Set Types
  • Global Rule Set: SAP-delivered, industry-standard rule set that offers a solid baseline — a good starting point.
  • Custom Rule Set: built from scratch to address an organization's specific risks and requirements.
Setup Options
  1. Use the SAP-delivered Global Ruleset. Path: GRC → Access Control → Access Risk Analysis → SOD Rules → Generate SOD Rules.
  2. Copy the delivered ruleset to create a custom ruleset and customize it.
    • Path: GRC → Access Control → Access Risk Analysis → SOD Rules → Download Rule Set.
    • Select the Risk IDs applicable to your organization based on the business process involved.
    • Prefix selected Risk IDs and Functions with Z; customize functions as needed.
    • Upload the file for the new custom ruleset and generate the rule set.
  3. Build a custom rule set from scratch. Path: NWBC → Set Up → Access Rule Maintenance.
    • Rule Sets → Create → enter name & description → Save.
    • Functions → Create → enter Function ID, business process, description → add actions & permissions (transactions & authorizations).
    • Access Risk → Create → enter Access Risk ID, business process & description → add functions → add the new ruleset → add a risk owner.
    • Once all Risk IDs are maintained → Generate Rule Set.
If only one ruleset exists (GLOBAL) and you upload a custom ruleset with OVERWRITE, GLOBAL is lost. To retain GLOBAL alongside a custom ruleset, use APPEND instead.
Rule Set Tips
  • Start with the SAP-delivered Global Rule Set and customize it to fit your organization.
  • Use a clear naming convention and description for custom rule sets.
  • Thoroughly test custom rule sets before moving them into production.

MSMP Rule Types

Initiator Rule
Directs an incoming request to a specific path — which path does it go down?
Agent Rule
Determines the approver — e.g. Manager, Role Owner, or others.
Routing Rule
Routes the request to another path when a special circumstance (a detour) is met, including SoD detours.
Notification Rule
Sends an email notification to the appropriate reviewers about request status.

SAP GRC Overview

GRC is a strategy and structure that helps organizations manage risk, comply with regulations, and achieve their goals.

SAP GRC enables organizations to manage regulations and compliance, and to remove risk from key operations.

Clear responsibility definitions, disciplined role provisioning, and tight control over super‑user access are critical to managing organizational risk.

Access Control (AC)

Mitigates risk in an organization — required to perform risk control as part of compliance and regulation practice.

Process Control (PC)

Manages compliance and policy management, letting organizations manage and monitor their internal control environments.

Risk Management (RM)

Manages risk activities and advance planning — identifying business risk and implementing measures to control it.

SAP GRC Access Control Modules
ARA

Access Risk Analysis

Identifies, monitors, and mitigates access & segregation‑of‑duties (SoD) risks to ensure compliance and reduce security vulnerabilities.

Types of risk
SoD RiskCritical ActionCritical Permission
  • SoD Risk: user has 2+ conflicting actions that enable fraud
  • Critical Action: the T‑code itself is a risk (e.g. SCC5, SM01)
  • Critical Permission: risk at field/value level (e.g. S_DEVELOP, S_USER_GRP with activity 02)
  • Remediation: preventive control
  • Mitigation: bypass SoD violations for a set period — detective control
Important tables
  • GRACFUNC Functions
  • GRACACTRULE SoD action rule detail data
  • GRACFUNCACT Rule set → function → action mapping
  • GRACSODRISKOWN SoD risk owner
  • GRACOWNER Master table, central owner admin
  • GRACUSERCONN Connector‑specific user (user–system relation)
Parameters (ARA)
  • 1007 Enable rule set change log
  • 1008 Enable role change log
  • 1027 Enable offline risk analysis (batch)
  • 1028 Include expired users
  • 1029 Include locked users
  • 1030 Include mitigated risk
ARM

Streamlines and automates user access requests, approvals, and provisioning — secure, compliant, efficient.

EAM

Emergency Access Mgmt

Controls temporary, high‑privilege access to critical systems — monitored "firefighter" access for emergency tasks.

Firefighter concept — granting access
  • ID based: normal user ID linked to FF ID for 1–5 days
  • Role based: FF role assigned to user ID for the request duration
Centralized vs. Decentralized EAM
Centralized EAM
  • User ID exists in both the SAP GRC system and the backend system
  • Emergency tasks initiated centrally via T‑code GRAC_EAM / GRAC_SPM
  • Users log on to the GRC system and use assigned Firefighter IDs (FFIDs) to reach backend systems
  • If GRC is down, emergency tasks cannot be performed in the backend
GRC downtime = blocked
Decentralized EAM
  • User ID exists in the backend system
  • Emergency tasks executed directly in each backend system
  • Firefighters log on to backend systems and act independently via /n/GRCPI/GRIA_EAM
  • Even if GRC is down, emergency tasks can still be performed in the backend
GRC‑downtime resilient
Controlled by Parameter 4015 Centralized → 4015 = NO  |  Decentralized → 4015 = YES
Important tables
  • GRACFFOWNER FF owners list
  • GRACFFUSER FF ID's users
  • GRACFFUSERT FF ID assignment details
  • GRACOBJECTT Text table, FF ID & role
  • GRAC_FFSESSION (T‑code) FF log review status
Parameters (4000 series — EAM/FF)
  • 4000 ID based or role based
  • 4001 Default firefighter validity period (days)
  • 4010 FF ID role
  • 4015 Centralized (NO) vs Decentralized (YES) EAM
BRM

Business Role Management

Creates, manages, and maintains business roles — defines, models, and controls access roles for compliance and reduced SoD risk.

Key features
  • Centralized role management
  • Role modelling and design
  • Workflow‑based role approval
  • Role versioning & history tracking
  • Segregation of Duties (SoD) analysis

GRC AC Ruleset Components

Ruleset
A collection of risk IDs that defines potential risks within an SAP system.
Risk ID
Identifies specific risks, each linked to actions that could lead to SoD conflicts.
Function
A grouping of critical actions or permissions that, when paired, may lead to conflicts.
Action
Transactions within functions that cause Critical Action or SoD risk.
Permission
Specific authorizations required to execute actions within a function.
SoD Risk
Arises when conflicting functions are assigned to the same user, breaching compliance.
